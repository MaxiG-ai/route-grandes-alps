# Plan: from one HTML file to a trip website

Goal: keep every bit of the prototype's behaviour (stage list, Leaflet map,
elevation profile, pass chips, Strava links, progress) and add a landing
page, a packing list, and lodging, a summary and photos per stage. The site
is in German; the repository is in English. Tricolore accents on white.

## 1. Where this started

`reference/index-original.html` (537 lines, 430 KB):

| Part | Size | Note |
|---|---|---|
| `ROUTES` (line 219) | **429 KB on one line** | 14 days × 310–800 track points (`lat/lon/ele/d`) plus waypoints, Strava, cols |
| `GAPS`, `PASSES`, `QD_PROFILE` | ~1.5 KB | hand-written content |
| CSS | ~250 lines | tokens, app shell, sidebar, map, profile, dark mode |
| JS | ~340 lines | Leaflet, SVG profile, sparklines, sidebar, init |

Track data was therefore 99 % of the weight. That is what the structure
hangs on: the landing page and the packing list must not pull 480 KB of
geometry, and a stage needs only its own track.

## 2. Decisions

| Question | Decision |
|---|---|
| Stage pages | **14 static pages** `day-01.html … day-14.html`, generated by `tools/build.py` from templates + `data/trip.json` |
| Track source | **GPX files in `gpx/`**, parsed during the build; distance, ascent, descent, elevation range and profile are derived, never stored twice |
| Data loading | `fetch()` + JSON — the host serves over HTTP, no `file://` constraint |
| Hosting | **Hetzner web hosting**, plain file upload, `index.html` at the root, relative paths only |
| Photos | in the repo, resized (max 1600 px) plus 400 px thumbnails |
| Site language | German only |
| Repository language | English: code, comments, filenames, JSON keys, CLI flags |

No build step at request time, no npm, no framework: `tools/build.py` runs
locally, its output is committed and uploaded. What sits on the server is
finished HTML.

**Widened while building:** the generator renders the landing page, the
stage overview and the packing list as well, not just the stage pages.
Otherwise three pages would fetch their content with JavaScript while the
14 stage pages ship ready-made — two mechanisms for the same job. Now there
is one: `python3 tools/build.py` writes all 17 pages and the 15 JSON files
the browser fetches.

A static multi-page site, still plain HTML + vanilla JS + Leaflet.

```
│   ├── packing-list.json       groups → items (weight, qty, note, verdict)
```

### Measured data vs. written content

The rule the whole thing rests on: **a GPX file is the single source for
every number**, and `data/trip.json` holds only what a track cannot know —
where the day started and ended, the date, the passes, the Strava links,
the lodging, the summary, the photo list.

That is why `trip.json` carries no distances or elevation figures at all.
They were duplicated there in the first draft; deriving them removes the
chance of the page and the track disagreeing. `data/tracks/*.json` is pure
build output and can be deleted at any time.

`data/trip.json` (excerpt):

```json
{

  "stravaProfile": "https://www.strava.com/athletes/11965636",
  "stages": [{
```

Photo paths follow a convention (`photos/day-07/…` and
`photos/day-07/thumbs/…`) to keep the manifest short.

### How the GPX numbers are derived

`tools/gpx.py` reads `<trkpt>`/`<ele>`, concatenates all `<trkseg>` (a stage
is one ride even when the recording was split) and collects `<wpt>` as
waypoints. Then:

1. **Smooth elevation** over 5 points. Raw GPS elevation is noisy enough to
   invent a few hundred metres of climbing over a long stage.
2. **Distance and climbing from the full-resolution track**, with a 1 m
   threshold against elevation wobble.
3. **Thin the geometry afterwards** (12 m minimum spacing, 1200 points cap)
   and rescale the per-point distances onto the full-resolution total, so
   the profile axis and the headline distance agree.

Step 2 before step 3 matters: thinning first cost about 1 % of both distance
and ascent in testing.

### The generator

`tools/build.py` fills the templates in `templates/`. No template
framework: `{{title}}`, `{{date}}`, `{{photos}}` and friends are replaced
with `str.replace`, and a leftover `{{` aborts the build.

Deliberately **pre-rendered into the HTML** (so it works without JavaScript
and each stage gets a real page title, `<meta description>` and share
preview): header, figures, pass chips, Strava links, lodging, summary,
photo grid, previous/next navigation and the stage strip.

Left to JavaScript: the Leaflet map, the elevation profile (which fetches
`data/tracks/day-07.json`, ~30 KB) and the lightbox.

The generator is idempotent and writes only what changed. `--check`
compares without writing and fails if a committed file is out of date
(`tools/upload.sh` calls it before uploading). `--today YYYY-MM-DD` pins
the ridden/today/planned date, `--smoothing N` tunes the elevation filter.

One consequence of pre-computing: the trip state freezes at build time.
Rebuild before uploading — noted in the README.

## 4. The pages

### `index.html`

Hero with title, route, dates and a cover image. Figures from the parsed
tracks: total distance, climbing, passes, kilometres ridden, progress bar
(the prototype's date logic, now evaluated in Python). Overview map of all
stages from `overview.json`, click a line to open that stage. Three entry
cards, then the full stage table.

### `stages.html`

All 14 as cards with a sparkline, date, state, distance, climbing and
passes — the prototype's sidebar, enlarged — plus the pass panel
("Gefahrene Pässe · 13", linked to quäldich.de).

### `day-NN.html`

1. Header: "Tag 7 von 14 · Sonntag, 5. September 2026", from → to, figures,
   gap note.
2. Map block: Leaflet plus the elevation profile with a linked cursor,
   terrain/streets toggle, start and finish markers, waypoint popups, pass
   chips, Strava links — **as the prototype behaved**, at a fixed height.
3. **Lodging**: name, type, place, price, rating, note, link, and a flag on
   the map.
4. **Summary**: paragraphs in a reading column (~64 characters).
5. **Photos**: responsive thumbnail grid, `loading="lazy"`, opening a
   self-built lightbox (arrow keys, Escape, swipe, caption). No third-party
   library, about 70 lines.
6. Footer: previous/next stage and a strip of all days.

### `packing-list.html`

From `data/packing-list.json`: groups (bags, sleeping, clothing, tools,
kitchen, electronics, hygiene, papers), each item with quantity, grams, a
note and `takeAgain: true | false | null` as the verdict after the trip.
Weight per group and in total, a split bar, jump links, and packing
checkboxes kept in `localStorage`.

## 5. German on the page

- `<html lang="de">`, all UI strings in the templates or in `format.js`.
- Dates: `Sonntag, 5. September 2026` and `So., 5. Sep.`, built from arrays
  rather than a locale, so the output does not depend on the machine.
- Numbers: `1.512 m`, `63,2 km` — dot for thousands, comma for decimals.
- Wording: Etappen, Tag 7 von 14, Packliste, Übernachtung, Zusammenfassung,
  Fotos, Pässe, Distanz, Aufstieg, Abstieg, Höhe, Gelände/Straßen, heute,
  noch nicht gefahren, Lücke im Track.

## 6. Colours (tricolore on white)

Tokens in `base.css`, no dark-mode blocks (`color-scheme: light`):

```css
:root{
  --white:#ffffff;       /* page background */
  --paper:#f6f7fa;       /* cards, panels */
  --line:#dfe4ee;
  --blue:#0055a4;        /* primary: links, current stage */
  --blue-deep:#003d78;   /* blue text on white, hover */
  --red:#ef4135;         /* accent: fills, edges, markers */
  --red-deep:#c8102e;    /* red text on white */
  --ink:#111827; --ink-soft:#4a5568; --ink-faint:#7b859b;
}
```

Contrast note: `#ef4135` only reaches ~3.6:1 on white, so red is used for
fills, edges and markers, while red **text** uses `--red-deep` (~5.9:1).
The tricolore stripe (blue/white/red) shows as a 3 px bar in the header and
along the hero image.

A happy accident: the profile's hypsometric ramp was already blue → white →
red and carried over unchanged.

## 7. Hosting on Hetzner

- Plain file upload into the document root: `index.html`, `stages.html`,
  `day-*.html`, `packing-list.html`, `assets/`, `data/`, `photos/`. Nothing
  else — `tools/`, `templates/`, `docs/`, `gpx/` and `reference/` stay in
  the repository.
- **Relative paths only** (`assets/css/base.css`, never `/assets/…`), so the
  site also runs from a subdirectory.
- Apache serves `.json` out of the box, so `fetch()` needs no configuration
  and no `.htaccess` — the one included merely sets cache times and
  compression.
- After uploading, open `day-07.html` directly: that shows immediately
  whether the relative paths and `data/tracks/…` are right.

## 9. Loose ends

- **The content is still to be written.** Lodging, summaries and photos are
  manual work. The build lays out the fields and fills them with quiet
  placeholders (`"summary": []` leaves the section out), so days can be
  filled in one at a time.
- **The extracted GPX files are a stopgap.** The prototype stored
  already-thinned tracks, so `gpx/*.gpx` is lower resolution than a fresh
  komoot or Strava export and the numbers come out about 1 % below what the
  prototype showed (1.251 km instead of 1.265 km in total). Dropping the
  real exports into `gpx/` and rebuilding fixes that.
- **Photo size.** 14 days × 10 images ≈ 40 MB in the repo — acceptable.
  Originals stay outside; `prepare_photos.py` produces the web sizes.
- **Leaflet is vendored** (150 KB) rather than loaded from a CDN: no
  third-party outage, and it works offline.
- **Fonts** (Fraunces, Archivo, IBM Plex Mono) still come from Google Fonts
  with solid fallbacks. Vendoring them would be the next step if that is
  unwelcome.
- **An all-days photo gallery** is easy to add once the manifests exist —
  not planned for now.
